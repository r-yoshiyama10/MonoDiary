## 1. 文書の目的とスコープ

本書は、LINE から日記エントリを送信し、LLM により**日記として読みやすい文章に整えて**蓄積・振り返りを行う個人用 Web アプリケーション「MonoDiary」の**要件を定義**する。実装の優先順位の根拠とする。

**スコープに含むもの**

- 機能要件（ユーザーが得られる価値・システムが提供する振る舞い）
- 非機能要件（性能、セキュリティ、運用・コスト方針の前提）
- 技術スタックとデプロイ前提

**スコープに含まないもの（別文書で扱う想定）**

- 詳細設計（API 仕様書、DB スキーマ確定版）
- UI モックの確定
- 運用手順書（Runbook）

## 2. プロジェクト概要

### 2.1 ビジョン

利用者は LINE で「今日あったこと」を**文章や箇条書き**で送る。バックエンドは **Gemini API** を用いて、それを**日記として自然に読める文体・構成**に整えたうえで保存する。**自分専用**の記録として Web 上で一覧・振り返りができ、将来の自分のための資産とする。

### 2.2 命名の由来

1. **Monologue（独白）** — 誰に見せるためではなく、自分だけの心の内を記録する場所。
2. **Diary（日記）** — 日々の記憶を保管し、未来の自分が振り返るための資産にする。

### 2.3 想定ユーザー

- **単一利用者（本人のみ）**。マルチテナントや一般公開サービスは対象外とする。

### 2.4 開発の位置づけ

「ものづくり」の実践として、バックエンドに **Go**、フロントエンドに **React** を採用し、**段階的に拡張**する。

## 3. 前提条件・制約

| 項目 | 内容 |
|------|------|
| ローカル開発 OS | macOS（Apple Silicon / arm64） |
| ローカル実行 | **Docker** を用いた開発環境を前提とする |
| インフラ方針 | 費用を抑え、無料枠の充実したサーバーレス / PaaS を活用する |
| 外部サービス | LINE Messaging API、**LINE Login**、Gemini API、PostgreSQL（本番は Supabase 等を想定） |

## 4. 技術スタック（方針）

※ 具体的なバージョン固定は実装開始時に `go.mod` / `package.json` 等で管理する。

---

## 5. 永続化方針

データは **PostgreSQL** に保存する。ローカルは Docker の PostgreSQL コンテナ、本番は **Supabase 等のマネージド PostgreSQL** を想定する。スプレッドシートを DB 代用する段階は設けない。

Web は**専用のログイン画面**を設け、**LINE Login** により本人のみが閲覧できる。

## 6. 機能要件

### 6.1 LINE 連携（入力）

| ID | 要件 | 備考 |
|----|------|------|
| F-01 | 利用者が LINE 公式アカウント（または同等の Messaging API チャネル）にメッセージを送信できる | **テキストメッセージのみ**を対象とする（画像・スタンプ・音声等は扱わない） |
| F-02 | バックエンドが Webhook でメッセージを受信し、日記エントリとして処理できる | 重複・再送対策は実装段階で検討 |
| F-03 | 受信した本文（箇条書き・断片的文章を含む）を **Gemini API** で**日記として読みやすい文章**に整え、保存用データに付与できる | 文体・長さ・一人称の扱い等はプロンプトまたは設定で調整可能とする。「短い要約」に限定しない |

### 6.2 データの保持

| ID | 要件 | 備考 |
|----|------|------|
| F-04 | 各エントリに少なくとも **送信日時**、**原文（LINE で送信したテキスト）**、**日記文体の本文（LLM 出力）** を保存できる | PostgreSQL に永続化 |
| F-05 | 将来の振り返りのため、**一覧取得** ができる | ページネーションは推奨 |
| F-06 | （任意・優先度は後続で確定）**日付範囲** やキーワードによる絞り込み | プロトタイプでは省略可 |

### 6.3 Web アプリケーション（認証・振り返り）

| ID | 要件 | 備考 |
|----|------|------|
| F-07 | **専用のログイン画面**を表示できる | UI は本サービス用に設計する（外部の埋め込みだけに依存しない） |
| F-08 | **LINE Login** により認証し、認証済みユーザーのみアプリ内コンテンツにアクセスできる | OAuth 2.0 等、LINE が定めるフローに準拠。セッション／トークンの扱いは詳細設計で定める |
| F-09 | ブラウザから日記エントリの**一覧**を表示できる | React + TypeScript |
| F-10 | 単一エントリの**詳細**（原文と日記文体の本文の対応）を確認できる | |
| F-11 | **本人のみ** が自分のエントリにアクセスできる | Messaging API の送信者と LINE Login ユーザーの**同一人物の紐づけ**（例: userId の対応）は実装設計で確定する |

### 6.4 管理・運用（最小）

| ID | 要件 | 備考 |
|----|------|------|
| F-12 | ローカルで Docker を用いてフロント・API・（必要なら）DB モックを起動できる | 具体的な `compose` 構成は別途 |
| F-13 | 本番・ステージング相当の環境変数で API キーや DB 接続を切り替えられる | シークレットをリポジトリに含めない |

## 7. 非機能要件

| ID | 区分 | 要件 |
|----|------|------|
| NF-01 | セキュリティ | LINE Messaging の署名検証、**LINE Login** のクライアントシークレット等の管理、セッション／Cookie の扱い、Gemini / DB の認証情報の安全な管理（環境変数・シークレット管理） |
| NF-02 | 可用性 | 個人利用のため高可用は必須としないが、ホスティング先のスリープ・コールドスタートは許容範囲を認識したうえで選定する |
| NF-03 | 性能 | 同期処理で十分とする（大量同時アクセスは想定しない） |
| NF-04 | 保守性 | Go / React の標準的なディレクトリ構成と、Repository 等のポート境界でテスト容易性を確保する |
| NF-05 | コスト | 無料枠内での運用を第一候補とし、有料化する場合は明示的に判断する |

## 8. 外部インターフェース（概要）

| 相手 | 方向 | 内容 |
|------|------|------|
| LINE Platform | LINE ↔ 自サービス | Messaging API Webhook（テキスト受信）、LINE Login（認可・トークン取得） |
| Gemini API | 自サービス → Google | 原文から日記文体への整形 |
| Supabase / PostgreSQL | 自サービス ↔ DB | データ永続化 |
| ブラウザ | ユーザー ↔ フロント | HTTPS 経由の API 呼び出し |

---

## 9. 用語

| 用語 | 説明 |
|------|------|
| エントリ | 1 回の LINE テキストメッセージ（またはそれに対応する保存単位）と、**原文**および **日記文体の本文（LLM 出力）** をまとめたレコード |
| 原文 | 利用者が LINE で送信したテキスト（箇条書き・メモ的な文章を含む） |
| 日記本文（LLM 出力） | Gemini により、原文をもとに生成した、日記として読みやすい文章 |

## 10. 未決定事項・次のステップ

以下は本要件定義の時点では**確定していない**ため、詳細設計またはプロトタイプ実装時に決定する。

1. **Messaging API の送信者と LINE Login ユーザーの紐づけ方法**（同一 LINE アカウント前提での userId 照合、初回連携フロー等）
2. **日記文体の具体的なルール**（文体「です・ます」固定か、長さの目安、日付の見出しの有無など。プロンプト設計で調整）
3. **マイグレーション運用**（SQL マイグレーションツールと GORM の役割分担。詳細設計で確定）
4. **認証セッションの実装**（サーバーサイドセッション、JWT、有効期限・ログアウトの扱い）

次に作成するとよい文書の例：**API 概要設計**、**データモデル（エントリ）定義**、**LINE Login / Webhook 連携フロー**、**Docker Compose 方針**。
